## 0. 结论

1. **现有 `nvn_be_*` 是回放核心的上沿，不是后端的下沿。** `hle_nvn.c` 调的 70 个 `nvn_be_*`（门禁「前端直调 mtl_ 0 处」守的就是这条边界）进来以后，命令解码、状态追踪、资源身份、变体选择、帧节拍和 Metal 调用全混在 `nvn_mtl.m` 一个文件里。安卓没有复用这份语义，而是在 `mtl_vk_shim.c` 里用 `mtl_*` 的形状把这 70 个入口重写了一遍，再经 `nvn_be_compat.h` 的 50 条宏转接到前端；底下 `vk_record.c` 又是第二个 OP 解码器。所以重复修的根子，在于下沿从来没有画出来过。vickwv 已同意这个分层方向。
2. **契约 = 新画的下沿 `nvn_gpu_*`**：60 个函数（含内联的 `nvn_gpu_ok`）、8 类不透明句柄、20 个能力位、14 个错误码。显示节拍源移出图形契约，放进平台接口 `nvn_vsync.h`（2 个函数）。
3. **契约词汇用 NVN 自己的记录**（`nvn_obj.h` 的状态记录、NVNformat、`nvn_refl.h` 的 `NVN_RB_*`），不另造中间枚举；NVN → 原生 API 只在后端里翻译一次。
4. **签名表和编译自洽不证明语义**。§3.2 的 7 条语义由 §8 的 24 条契约用例在实现期回归（D2 起每一步各跑与本步相关的那几条）。

## 1. 分层

```
前端  hle_nvn.c（NVN）/ hle_vk.m / egl.m
  │  nvn_be_*（上沿；形状基本不变，见 §2.2）
  ▼
回放核心（只写一份，纯 C，不 include 任何图形 API 头）
  ├ 命令解码        OP 流 → 调度（CALL/JUMP/END、拍平、前瞻索引）
  ├ 状态追踪        S / R 状态块、脏位、绑定快照

  ├ 宽屏挂点        widen_glue.inc
  └ 帧节拍          上屏队列、interval / hold / 选帧 / 虚拟拍、限帧（nvn_pace.h / nvn_fps.c）、呈现时刻账
  │  nvn_gpu_*（下沿，nvn_backend.h）             nvn_vsync_*（平台节拍，nvn_vsync.h）
  ▼                                               ▼
后端  Metal │ Vulkan                              平台  CAMetalDisplayLink │ AChoreographer │ 无（核心用 nvn_pace 计时）

```

判定规则（第一性原理）：一段代码换成 Vulkan 以后还要不要原样存在？要，就进核心；只有换个 API 才需要重写的，进后端；既不是图形 API 也不是 NVN 语义的（显示节拍、窗口租约、线程 QoS），归平台层。

### 3.2 定稿前补清的 7 条语义（vickwv A1–A7；头文件注释与本节一致，对应用例见 §8）

**A1 完整反射过下沿。** aid 不能当 Vulkan binding。`nvn_gpu_shader_src` 带一份已核对的中间布局 `nvn_gpu_layout`：每项写 set / binding（编译器写进 blob 的原值）、资源类别（9 类）、数量、可见阶段、来源（`nvn_refl.h` 的 `NVN_RB_*` + NVN 槽号）、访问（R / W / RW）、Metal aid；整张布局还带 push 范围、support 缓冲长度，以及身份（编译器产出 blob 时写下的 16 字节摘要 + 来源名）。
- 后端装载时与 blob 自带的反射逐项核对，对不上就报 `NVN_GPU_E_LAYOUT`，不许自行重排（例如把已编 SPIR-V 私自改成每阶段一个 set）。
- 四个 set 是安卓现行 direct ABI；Metal 忽略 set、用 aid，不要求 Metal 也分四个 set。
- `nvn_gpu_bind` 按布局项下标绑定，类别必须一致。
- 超出 push 范围的大块，放进布局里已声明的 support 项，用 arena 切片绑上。上传方式和布局一起由编译器定，不能只换上传方式。（C16 C17）

**A2 唯一设备与能力来源。**
- `nvn_gpu_open` 接管平台层已建好的设备（安卓：Prepare 按 profile 建好的设备上下文），不另建设备，也不拥有它的寿命。先后顺序：平台 Prepare → `open` → 平台给窗口（WSI 租约）→ `surface_attach`。窗口租约归平台层，后端不自己去要窗口。
- `nvn_gpu_caps` 只从同一份「已启用能力记录」派生（安卓就是 `device_caps.c` 用的那份），`caps_id` 是这份记录的摘要。每个限值都在注释里写了来源字段：UBO / SSBO 偏移对齐与 range、每阶段每类描述符上限、可绑定 set 数、存储 / 原子可用的阶段。格式用途按格式查。
- 基线是 Vulkan 1.1 + 二元信号量 / 栅栏；时间线信号量、设备地址、动态状态、GPL 都是可选能力，缺了只是对应能力位为 0。v1 注释里「缺时间线即失败」的例子已删除。（C18）

**A3 release 与 backing 的最后使用。** 「使用」分四种：
- ① 已录制进未提交的 cmd；
- ② 已提交、尚未完成的 cmd；
- ③ 后端自己的后台工作（上传暂存、管线编译读着色器、present blit）；
- ④ 经 GPU 地址的间接引用——后端看不到，由核心对每个这样的缓冲调 `nvn_gpu_buf_use` 声明，声明即保活（Vulkan 可以省驻留操作，不能省保活）。

release 随时可调，真正销毁推迟到最后一次使用结束。池 Finalize 时核心调 `nvn_gpu_buf_release(b, retired, user)`：后端持有包装与宿主页，直到最后一次使用结束才解除并调 retired；核心在 retired 之后才允许宿主解除或复用这段 backing。`cmd_abort` 丢弃的 cmd 的引用随之解除。（C05 C06 C07 C08）

**A4 失败不能被更大的完成值覆盖。** 选「终止后续」，不选「记失败区间」。
- 规则：第一个失败段的 signal 记为 F。之后的每一段（已提交的和以后要提交的）都不执行，各以 FAILED 回调一次；已完成值永远停在 F 之前；`fence_wait(v ≥ F)` 返回 `NVN_GPU_E_FAILED`。1 成功、2 失败、3 尝试时，`wait(2)` 和 `wait(3)` 都返回 FAILED，`wait(1)` 返回 OK。
- 理由：NVN 队列严格按序，后面的段读前面段的 GPU 结果。前面一段没执行，后面的「成功」就建在缺失的内容上，发布它就是假成功。如果记失败区间，等于允许后续段在缺失内容上继续发布完成，核心还得再判一次「后面的段读没读到失败段写的东西」——这个判断做不准。这也是安卓 `g_lost_from_fence` 现行的口径。恢复只能关会话重开。
- 区分 FAULT：段已执行完、只是 GPU 报了故障（Metal `cb.error` 非设备丢失类），这时不终止，时间线照常推进、回写照做、隔离由核心定。这保持 Metal 现行行为，因为抽离是纯重构。
- 失败段的回调恰好一次，`status = FAILED`，核心不做任何成功回写（事件值、计数器、遮挡结果都不写），遮挡指针为 NULL。
- 发布顺序：成功段是「GPU 完成 → done（核心回写）→ release 语义推进已完成值」；失败段是「release 语义发布 F → done(FAILED)」。`fence_done` / `fence_failed` / `fence_wait` 都以 acquire 语义读。
- 未提交的 cmd 在 Stop / OOM 时由核心 `cmd_abort`：不执行、不回调、不推进；`close` 的第一步也是丢弃全部未提交 cmd。（C02 C03 C04 C08 C23）

**A5 out-of-date、撤销和退休。** v1 的单个 E_STATE 拆成三个：
- `NVN_GPU_E_OUTDATED`：可重建。调用方 `surface_rebuild` 得到新 generation 后重试。
- `NVN_GPU_E_REVOKED`：已撤销。不可在原窗口上重建，等平台给新窗口。
- `NVN_GPU_E_ORDER`：顺序错误，是核心的错，不可重试。

generation 从 1 起单调递增，每次 attach / rebuild 加 1，`surface_gen` 为 0 表示已撤销。

drawable 的所有权：
- `acquire` 成功后归调用方，必须且只能经 `present` 或 `drawable_release` 交回一次；
- `acquire` 失败（含 TIMEOUT）时调用方不拥有任何 drawable；
- `present` 无论返回什么都已交回；
- 旧 generation 的 drawable 交给 `present` 返回 OUTDATED。

`close` 返回 OK 之前必须做完六件事：
1. 丢弃未提交 cmd；
2. 已提交段的 done 各调过恰好一次；
3. 所有 present 退休、presented 各调过恰好一次；
4. 后台 worker 停下并 join；
5. 返回之后不再有任何回调；
6. 管线缓存落盘。

做不完返回 TIMEOUT，资源保留；再调一次 close 接着做。`surface_detach` 同理：TIMEOUT 时调用方必须保留窗口租约。（C09–C13）

**A6 时间域与缺测。**
- 完成回调用 `time_kind` 区分三档：NONE、DURATION（只有 `gpu_dur_ns` 可信）、HOST（起止时刻已校准到主机单调时钟，要 `CAP_GPU_TIME_HOST`；Metal 恒有，Vulkan 要 calibrated_timestamps）。不可信的字段为 0，0 不表示零耗时。
- 实际上屏时刻是单独的能力位 `CAP_SHOWN_TIME`。`nvn_gpu_shown.status` 分 SHOWN_AT / DROPPED / UNKNOWN，未知和丢弃都不会和某个时刻值混淆。
- 不许拿 CPU 端 present 返回的时刻或渲染完成栅栏冒充上屏时刻。
- 上沿的 `nvn_be_presented_time` 现有约定（0 = 还没好、-1 = 丢弃）在核心里由 status 换算，前端不变；UNKNOWN 对前端报 0，表示一直没有读数。（C14）

**A7 能力位与错误域不串用。**
- `CAP_LINKED_PIPE` 只在后端有「输出与完整版逐像素相同」的链接版时置位；只有 GPL 不算，要有与 Metal 链接桩等价的实现，并且过了 C19。
- 片元读回按格式开（`NVN_GPU_FMT_FB_FETCH`）；存储 / 原子按阶段开（`caps.storage_stages` / `atomic_stages`），原子格式再看 `NVN_GPU_FMT_ATOMIC`；动态状态拆成深度模板（`CAP_DYN_DEPTH_STENCIL`）和光栅（`CAP_DYN_RASTER`）两位。
- 错误码改到独立区间 [-1099, -1000]（14 个码），与安卓 native–NativeAOT 会话 ABI（`s2a_direct_result`：+1 … -9）不相交。返回值类型是单成员结构体 `nvn_gpu_rc`，赋给 int、cast 成 int 都编译不过；接点处只能经 `.code` 按 §3.3 的表显式映射。单测有区间检查和两条「必须编译失败」的探针。v1 的撞值（Pending -7 = Driver、Timeout -5 = Stopped）在 v2 里不可能再出现。（C15）

**#968 消费审查两项定稿（10-30，画面线；头文件同步）。**
- ① `nvn_gpu_binding.u` 加 `ts { view; samp; }`，组合采样贴图（`NVN_GPU_RES_TEX_SAMP`）只认 `u.ts`，两个句柄都不得为空。v2 原稿 union 里只有分开的 `view` / `samp`，组合项一次只能装下一个。各类别取哪个成员写在头文件注释里，取错或缺一个是粘滞 `E_LAYOUT`。
- ② `signal` 必须严格大于上一次合法提交的值，所以从不为 0（删掉原稿 `nvn_gpu_done.signal`「0 = 本段不推进」：核心每次提交都带栅栏值，不需要不推进的段）。违约时返回 `E_ARG`，本段不提交，并按失败处理：先发布 F = 上一次合法 signal + 1（已有更小的 F 就保持），再以 FAILED（rc = `E_ARG`）回调本段恰好一次，之后同 A4 终止。
  - 理由：被拒的段等于严格按序的队列里缺了一段，和没执行的段同理，后面的段可能读它的结果。F 取「上一次合法值 + 1」，以后任何合法 signal 都 ≥ F，等它们都报 FAILED。
  - 「只返回 E_ARG、不发布 F、不回调」会让核心等这一段的 done 永远等不到，它的回写和资源退休也悬空，所以不采用。用例见 §8 C25 / C26。

## 4. 9 处「待议」的定稿（按 vickwv 的倾向；头文件里已改成「定稿 #n」+ 理由）

## 7. 读码时顺带发现的问题（后续项，本次不修；v2 按 vickwv 核对更正）

- **安卓后端 period / 显示 tick / hold 链未完整接通**（v1 写成「安卓不限帧」，不准确，已更正）。
  - 后端侧：`mtl_present` 丢弃 `period_s`（shim @603–605），`link_active` / `link_wait_tick` 恒 0（@830–831）。
  - 前端侧：`hle_nvn.c` 仍按 `nvn_pace` 限节拍。present 时算出 `o->avail[idx]`（642ec4574 `hle_nvn.c` @2179–2190），Acquire 时按它 `sleep_until_ns`（@1657–1674）；安卓 `compat/mach/mach.h` @64–67 把 `mach_wait_until` 映射到真实的 `clock_nanosleep`。
  - 缺的是后端那一段：按显示刷新按住 N 拍、按实际上屏时刻对账。具体 30 帧 / 三拍的语义要核实际配置和 interval 1 / 2 / 3 的显示读数，不只看 shim 一处参数。
- **`tex_gpu_owned` 恒 0 的风险链**（shim @582）：前端 `nvn_ft_poll`（`hle_nvn.c` @447，@463：`!nvn_be_tex_gpu_owned(serial)` 时调 `nvn_be_tex_cpu_written`）→ shim `mtl_tex_cpu_written` @580 → `s2a_vk_adapter_tex_release` → texcache 丢弃（`nvn_vk_texcache.c` @927 清 `gpu_written`），下次就会从旧的 CPU 内容重建。texcache 普通重传路径本来有 `!gpu_written` 保护（@635、@736），所以只看它内部的标志不够。
  - 反例走「GPU 写图 → 共享 / 相邻页变脏 → 前端 poll → 再次采样」，正例保留真实 WriteTexels 更新（用例 C21）。
  - 目前没有该反例的真机输出，不把它定为历史紫绿 / 闪回的已证根因，也不因为计划抽核心就宣布已修。
- **`mtl_sub_fill` 语义不对**：安卓 shim @464 用 `memset(value & 0xFF)` 按字节填，NVN ClearBuffer 是 32 位样式填充（Metal 侧 `mtl_sub_fill` @1367 按 32 位做）。全仓库没有调用方；它的实际消费者另核，D9 退役，不扩展 shim。契约 `nvn_gpu_fill_buf` 已写死 32 位语义，验收用 0x11223344（用例 C01），不能只用 0x5A5A5A5A——那个值每字节相同，按字节填也会碰巧对。
