# G05：Mac 存档备份、恢复与 G06 格式契约

关联 #58 / G05。此文定义 `S2ArmSave` v1，供 G06 先用合成输入开发；不表示 iOS 导入/导出或跨设备游戏读档已经验收。

## 玩家入口

游戏详情 →「存档备份与恢复…」。先停止游戏和其他构建任务；备份/检查/恢复与启动共用游戏库 execution 锁，命令行调用也不能绕过。该功能不需要游戏密钥、SDK、Xcode 或引擎工具初始化。

- 备份：选择游戏库、应用数据目录以外的位置，生成 `.s2asave` 文件。同名文件拒绝覆盖，原存档不变。
- 恢复：选择备份，先检查完整性并显示游戏、版本、备份时间、用户标识及文件数/大小，再确认恢复。确认与实际执行之间备份、游戏库或目标内容变化时，必须重新检查。
- 恢复前自动保留可再次选择的 `before-restore.s2asave`，并原样保留此前的数据根。界面可在访达中显示最近一份备份；没有自动清理原副本的流程。
- 失败的任务「重试」回到检查界面，不自动再次覆盖存档。

## 数据边界与布局

`pack/jobs/build.py:runtime_env` 把每款游戏的 `S2A_RYU_DATA` 指向 `<游戏库>/saves/<gameId>`。此根包含 Ryujinx 数据，不是 `S2A_SAVE_DIR` 的 `account/`、`device/` 测试种子目录。**不调用测试种子接口，也不修改游戏运行时 ABI。**

v1 白名单包含：

| 相对数据根路径 | 原因 |
|---|---|
| `bis/user/save/**` | 已提交的账号/设备存档、目录元信息 |
| `bis/system/save/**` | 与上述存档配套的 LibHac 系统存档/索引；不能只拷进度文件 |
| `system/Profiles.json` | Ryujinx 用户显示资料；只用于为索引用户号配显示名，`last_opened` 不判归属 |

原始依据：`services/S2A.Services/Saves.cs` 的已提交目录读取、`compat/tree/.../AccountSaveDataManager.cs` 的 `system/Profiles.json` 和 `VirtualFileSystem.cs` 的 User/System 存档空间。Mac 已按游戏隔离整个数据根；本格式不从共享的多游戏 Ryujinx 目录猜测单款存档。

导出不包含 `system/prod.keys`、游戏资源、固件、运行日志或着色器缓存。恢复时暂存当前数据根，替换白名单内的完整子树，保留其他数据。内部原副本是原数据根，仍只在本机游戏库内保存，不作为诊断内容导出。

## `.s2asave` v1

ZIP（stored/deflated，允许大文件使用 ZIP64）；包含根 `manifest.json` 及清单列出的 `payload/<相对路径>` 普通文件。空目录由 manifest 记录，不用 ZIP 目录条目。所有实际条目必须与清单完全一致。ZIP64 使用标准相邻 EOCD/locator，不接受前置数据或可扩展 EOCD 记录，并在加载中央目录前独立检查 64 位计数和大小上限。

```json
{
  "format": "S2ArmSave",
  "schema": 1,
  "layout": "ryujinx-data-v1",
  "platform": "macos",
  "createdAt": "2026-10-23T12:00:00+00:00",
  "game": {
    "id": "0100000000000000",
    "name": "合成示例",
    "version": 1,
    "contentIdentity": "<pack/jobs/library.py input_identity 的 SHA-256>"
  },
  "users": {
    "ids": ["00000000000000010000000000000000"],
    "active": "00000000000000010000000000000000"
  },
  "saveEntries": [
    {"saveId": "0000000000000001", "programId": "0100000000000000", "type": "account", "userId": "00000000000000010000000000000000"}
  ],
  "deviceSettings": {},
  "directories": ["bis/user/save", "bis/user/save/0000000000000001/0/empty"],
  "files": [
    {"path": "bis/user/save/0000000000000001/0/progress.bin", "size": 128, "sha256": "<64 位小写十六进制>"},
    {"path": "system/Profiles.json", "size": 256, "sha256": "<64 位小写十六进制>"}
  ]
}
```

示例只说明字段，文件大小与散列是占位值，不是可导入备份。可执行 fixture 由 `pack/jobs/tests/test_saves.py` 在临时目录生成。

- `game.id` 为游戏库登记的 16 位十六进制 baseId；`version` 为选中本体/更新的最大原始版本号；`contentIdentity` 直接复用既有函数，覆盖当前选中本体、更新和 DLC。恢复要求三者一致，不自动升级、降级或重映射。
- `saveEntries` 为可选字段，每个账号/设备存档一条，四个键分别是存档号、程序号、`account|device`、用户号。来源唯一为已提交的 `bis/system/save/8000000000000000/0/imkvdb.arc`；不读取工作副本 `/1` 来兜底。`bis/user/save/<saveId>/0/` 对应真机种子 `account/` 或 `device/` 的已提交内容；设备存档用户号为 32 个零。多账号必须逐条保留，不能合并为当前用户。非正常状态、非主槽、缺失/损坏/未知索引及未被索引覆盖的存档目录一律报错，不猜归属。
- `users.ids` 现在是索引中账号存档所属用户的去重集合，`active` 仅为兼容现有前端的显示代表（首个排序用户；仅设备存档时为空），不代表当前用户。Profiles 只供显示名；用户可不在 Profiles 中，当前用户不同、目标多了 profile 均不拒绝。恢复按相同程序号和类型的存档所属用户集合比较，不按存档序号或整组 profile 比较，禁止静默改绑。
- `deviceSettings` 为可选对象，键 `system_time`、`language`、`region`、`timezone` 各自也可省略，值为原始设置字符串（最多 256 字符）。Mac 无可靠来源时写 `{}`，不编造当前时间或系统设置。导入仅保存并校验此元信息，不修改宿主时钟、语言、地区、时区；G06 应按真机契约显式消费并验证游戏行为。
- 旧 schema 1 清单缺少 `saveEntries` / `deviceSettings` 时仍可读取：从其 payload 的现有已提交索引重新得出归属，设备设置视为 `{}`，忽略旧 `users.active` 对归属的暗示。新清单的 `saveEntries` 必须逐字等于从 payload 推导的映射，不能通过伪造清单改变用户。索引缺失的旧包不能安全识别归属，必须报红而不是恢复成功兜底。schema/layout 不变。
- 文件路径为 NFC、POSIX 相对路径。拒绝绝对路径、`..`、反斜杠、控制字符、冒号、尾部空格/点、重复/大小写冲突、文件/目录冲突、链接及特殊文件。原数据中的链接也拒绝，不向外遍历。
- 上限：20,000 文件、20,000 目录、32 GiB 解压数据、8 MiB manifest/用户资料、32 层路径。加载 ZIP 中央目录前检查计数/目录大小，逐文件检查大小、CRC 与 SHA-256；拒绝额外条目、重复 JSON 键、加密条目、未知 schema/layout 和不支持的压缩算法。
- 散列用于完整性和确认后防变更，不是来源签名，也不能证明保存内容的游戏语义。G06 应复用验证规则；不同引擎/LibHac 布局需要显式迁移和新 layout，不能只改扩展名。跨设备真实读档仍须另行验收。


## LibHac 索引与附加元数据依据

原上游 `Thealexbarney/LibHac` 当前无法访问。核查使用公开 LibHac 源码镜像固定提交 [`hyjinx-emu/Hyjinx@3536d77c`](https://github.com/hyjinx-emu/Hyjinx/tree/3536d77cf02a8debfeabafc017182247627cd6ed/src/Hyjinx.LibHac)，并用本项目实际依赖的 NuGet LibHac **0.19.0** 独立合成探针交叉核对结构大小、偏移与目录文件行为；镜像不作为本项目新增依赖。

- [`Kvdb/KeyValueArchive.cs`](https://github.com/hyjinx-emu/Hyjinx/blob/3536d77cf02a8debfeabafc017182247627cd6ed/src/Hyjinx.LibHac/Kvdb/KeyValueArchive.cs)：`IMKV` + reserved + entryCount，`IMEN` + keySize + valueSize，均为小端 32 位；条目紧接 key、value，不插对齐。`FlatMapKeyValueStore` 用 `imkvdb.arc` 保存原始结构字节。
- [`Fs/Common/SaveDataTypes.cs`](https://github.com/hyjinx-emu/Hyjinx/blob/3536d77cf02a8debfeabafc017182247627cd6ed/src/Hyjinx.LibHac/Fs/Common/SaveDataTypes.cs) 和 [`FsSrv/SaveDataIndexerValue.cs`](https://github.com/hyjinx-emu/Hyjinx/blob/3536d77cf02a8debfeabafc017182247627cd6ed/src/Hyjinx.LibHac/FsSrv/SaveDataIndexerValue.cs)：key/value 都是 0x40 字节。key 的程序号在 0、用户高/低半部在 8/16、类型在 0x20；value 的存档号在 0、空间在 0x18、状态在 0x19。`SaveDataIndexer.GenerateSaveDataInfo` 用这些字段生成存档描述。UserId 是两个小端 u64，但显示字符串为 high/low 各 16 位十六进制拼接，不是简单反转整段 16 字节。
- [`FsSystem/DirectorySaveDataFileSystem.cs`](https://github.com/hyjinx-emu/Hyjinx/blob/3536d77cf02a8debfeabafc017182247627cd6ed/src/Hyjinx.LibHac/FsSystem/DirectorySaveDataFileSystem.cs)：附加元数据是**每个存档目录根**的 `ExtraData0`（已提交）、`ExtraData1`（修改中）、`ExtraData_`（提交同步中）。`InitializeExtraData` / `CommitExtraDataImpl` 管理这些文件，`WriteExtraDataImpl` 原样写入 `SaveDataExtraData`（含 Attribute、OwnerId、TimeStamp、DataSize、JournalSize、CommitId），不是集中存放在系统索引里。
- 因而用户存档的附加元数据主要在 `bis/user/save/<saveId>/ExtraData*`，系统索引自身的附加元数据在 `bis/system/save/8000000000000000/ExtraData*`。G05 同时备份两棵完整子树，原样携带已有文件；仅备份 `bis/system/save` 不足以覆盖用户存档附加元数据。本实现不合成缺失元数据、不重建容量或时间戳。

`tests/真机契约.md` 已随最新主线提供：`S2A_SAVE_DIR` 是清空再播种测试接口，存档侧车还含 `user/system_time/language/region/timezone`。上述映射只为 G06 留契约，不在 G05 调用该破坏性接口。

## 任务接口

沿用 schema 1 的本地 JSON 请求与 NDJSON 事件；不是新增运行时日志协议。请求包含原有 `privateRoot`、`library`、`libraryId`、`gameId`，密钥/源码路径均无需传入。

| operation | 附加输入 | result |
|---|---|---|
| `saveStatus` | 无 | `hasSave/fileCount/totalBytes/users/previousBackup/recovered` |
| `saveBackup` | `path`：新备份文件 | `outputPath/fileCount` |
| `saveInspect` | `path`：待检查 ZIP | `manifest/archiveSha256/targetFingerprint/previewLibraryId/fileCount/totalBytes/notice` |
| `saveRestore` | `path` 与上一步的三项校验值 | `committed/hadOriginal/outputPath/previousBackup` |

例如创建权限为 0600、归当前用户所有的请求后：

```sh
python3 -B pack/jobs/main.py --request <请求.json>
```

通用游戏库锁失败仍按原任务机制报错；本模块具体拒绝原因使用 `save_empty`、`save_exists`、`save_space`、`save_wrong_game`、`save_version`、`save_wrong_user`、`save_changed`、`save_invalid`、`save_recovery` 等错误码。不将存档正文写入事件或诊断。

## 恢复事务与取消

1. 持有 execution/catalog 锁，先处理此前未完成事务，再完整校验备份、目标和确认值。
2. 检查暂存及保留副本所需空间；生成并验证恢复前 ZIP。在同一游戏库磁盘内暂存现有数据根，替换白名单文件，校验每个写入文件并 fsync。
3. 写入 `<游戏库>/save-transactions/<gameId>.json` 的 `prepared` 意图记录；路径只由游戏号和随机事务号派生，事务目录另有匹配 owner 记录。
4. 把原数据根重命名到 `<游戏库>/save-backups/<gameId>/<事务号>/data`，再将暂存数据根重命名到正式位置。两次重命名之间取消或失败，先回退原目录。
5. fsync 后将 journal 写为 `committed`，这是提交点。此后到来的取消不谎报成“未恢复”；保留恢复结果及原副本。提交后清理失败只发 `save_cleanup` 警告，保留 journal 供下次检查处理。
6. 进程被强制终止时，下一次存档操作或启动游戏之前检查 journal：未提交的恢复回退原目录，已提交的保留新目录；无法确定或无法回退时阻止启动，保留现场。不会尝试猜测或删除原副本。

未写入意图记录就中断时可能留下私有暂存/备份目录，原数据未动；不自动删除不明目录。实现使用 fsync 和同盘重命名，测试覆盖真实子进程强制退出；不能将它写成所有文件系统、拔盘或实际断电已验收。

## 验证边界

自动测试使用合成存档及原有文件布局，验证字节往返、索引/用户保留、拒绝路径、取消、互斥、不同提交阶段的真实进程退出和启动前恢复。另做真实 Mac GUI 点击与打包验证。没有玩家可运行游戏与自有测试存档，**游戏恢复后读取原进度的端到端验收待补**；G06 的 iPhone↔Mac 真实往返同样待其实现与设备验证。

## 导入社区存档（10-27）

「恢复存档」除了本工具的 `.s2asave` 备份，也接受社区常见的存档布局（文件夹或 zip）：JKSV、Checkpoint、yuzu、Ryujinx，以及直接是游戏存档文件的文件夹。识别规则在 `pack/jobs/save_formats.py`（命令行导入器 `tools/save_import.py` 用同一份）。

- 前提：这款游戏在启动器里运行过一次并存过档（数据根里已有它的存档位置）。还没有时提示「请先运行一次游戏并存档，再导入」，不会自己新建存档条目。
- 做法：只替换这款游戏已有存档条目（同程序号、同类型）提交槽里的文件，存档索引、用户资料、其他游戏的存档都不动；先转成一份本游戏的 `.s2asave`，再走上面同一套检查、预览、恢复与回滚。转换结果缓存在 `save-imports/<游戏>/`，检查和恢复用的是同一份。
- 拒绝：存档属于别的游戏（程序号对不上）、一个来源里认出几款而无法确定、zip 越界路径或链接、同一游戏有多个用户的存档（暂不支持选择）。
- 结构存疑：社区存档里只有一个子目录 `0/`、又比不出该不该剥（没有这款游戏自己的存档可比，或剥 / 不剥两种解释都对得上）时，按不剥导入，并在 `saveInspect` 的 `notice` 里给一句玩家能懂的话（`pack/jobs/saves.py` 的 `STRUCTURE_NOTICE`），界面在确认恢复前显示。`notice` 只做提示，不参与任何判定，`saveRestore` 不因它拒绝。提示与转换结果一起缓存在 `save-imports/<游戏>/<键>.notice.json`；命中缓存时不重跑识别，靠这个小文件取回同一句。

## iOS 单包手动导入存档（10-30）

**单包（`oneclick.sh` 出的 `.ipa`）没有启动器**，所以上一条的「恢复存档」界面不存在 —— 那条路只在 Mac 游戏库形态里有。单包只能手动放文件，本文给出确切路径与判据。

### 前提：先跑一次并存一次档

**`saveDataId` 是「游戏真的写过存档」时才由 `S2A.Services` 分配的**（16 位十六进制，如 `0000000000000001`）。**没存过档 → 目录不存在 → 没地方放。**

做法：进游戏 → 走到能存档的地方 → 存一次 → 退出。

### 数据根（iOS 默认）

`services/S2A.Services/Exports.cs` 的 `baseDir` 三级回落：`configuration.StateDirectory` → `S2A_RYU_DATA` → `SpecialFolder.Personal/S2A/ryujinx`。**单包出包时 `pack/oneclick/*.sh` 不设 `S2A_RYU_DATA`**，所以落到第三级；iOS 的 `SpecialFolder.Personal` 是 App 的 `Documents`：

```
<App Documents>/S2A/ryujinx/bis/user/save/<saveDataId 16 位十六进制>/0/
```

**能不能在「文件」App 里看到**：ipa 的 `Info.plist` 里 `UIFileSharingEnabled` 与 `LSSupportsOpeningDocumentsInPlace` 都是 true（`io.s2arm-exp.01007EF00011E000` 实测），所以「文件 → 我的 iPhone → <App 名>」能进去。

### 从 yuzu / Eden 存档搬过来

yuzu 系布局是 `…/nand/user/save/0000000000000000/<32 位用户号>/<程序号>/`，`save_formats.py` 认得（`yuzu` 布局，用户号全 0 = 设备存档）。**但两边不能直接拷目录**：

| 格式 | 路径 | 游戏怎么找到它 |
|---|---|---|
| yuzu / Eden | `nand/user/save/<saveId>/<userId>/<titleId>/` | **按 titleId 分目录**，人可读 |
| Ryujinx / S2Arm | `bis/user/save/<saveDataId 16 位十六进制>/0/` | **`saveDataId` 是随机 ID**，靠同级 `ExtraData0` 开头 0x40 字节的存档属性（程序号 u64、用户号 16 字节、类型 u8 在 0x20）映射 |

**`saveDataId` 与 yuzu 的用户号/程序号没有对应关系** —— 拷目录会让游戏找不到存档。要拷的是**内容**：把 `<titleId>/` 下的槽位目录（01007EF00011E000 是 `0/`…`5/`）直接放进 `bis/user/save/<saveDataId>/0/` 下：

```
bis/user/save/000000000000000X/0/0/   ← 槽位 0
bis/user/save/000000000000000X/0/1/   ← 槽位 1
```

**注意「唯一子目录 `0`」这个歧义**：`save_formats.py` 的注释写明，`0/` 既可能是 Ryujinx 的提交目录，也可能是游戏自己的槽位目录（01007EF00011E000就是 `0/…5/`）——判断依据是「这款游戏自己写出的存档顶层」。手动拷贝时这一层要按游戏实际槽位来，**别把游戏槽位当成 Ryujinx 提交目录再套一层**。

### 不要用 `S2A_SAVE_DIR` 代替

`runtime/run_mac.sh` 注释写明它是测试/导入种子，**启动时会清存档**（"`S2A_SAVE_DIR` is a test/import seed that clears saves at boot; never set it for normal play"）。正常玩不要设。

### 已知限制

- **没有界面提示**：路径写错、槽位放错、`saveDataId` 没分配，游戏只会表现为「没有存档」，不会报错。
- **没有回滚**：手动拷贝前请自己备份 `bis/user/save/<saveDataId>/`。
- **跨设备一致性未验收**：`docs/存档备份_G05.md` 的「验证边界」一节已注明「G06 的 iPhone↔Mac 真实往返待其实现与设备验证」，本文这条手动路径同样没有端到端验收记录。

### 时效说明（以 main `c0695564` 为准）

**上文的路径结论基于 `c0695564` 的 `main`。** 平台 adapter P6（`#1073`）会把存档目录改成**由平台装配显式给出**（`HostConfiguration.SaveDirectory`），届时本节「`Exports.cs` 三级回落 → `SpecialFolder.Personal/S2A/ryujinx`」这条不再成立，**以新实现为准**。

**判断方法**：看 `services/S2A.Services/HostConfiguration.cs` 有没有 `SaveDirectory` 字段、以及 `pack/oneclick` 出包时有没有把它填进去；填了就以那个目录为准，本文的 `S2A/ryujinx` 只是「没填时的缺省」。
