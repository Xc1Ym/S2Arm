# 直连架构（直连线；10-24 调研选型，10-25 起为在用架构）

> **现行架构（10-25）**：直连 = 游戏的图形调用在图形接口层直接翻成 Metal，不模拟 Switch GPU。NVN / Vulkan / OpenGL 三个前端共用一个直连公共后端（命令编码、资源、同步、上屏、宽屏挂点；Metal 4 / Metal 3 按设备能力选路）和一条离线着色器链。出包时自动推导每款配置、离线翻译着色器；运行时缺的着色器现编一次、跨局复用，缺的管线组合按画布格式补变体；直连崩溃或画面异常（游戏的绘制被持续丢掉）整局退回通用模式，下次起局告知玩家。回放层、离线链与普查脚本都是我方代码，按这套架构演进：改到哪块就按我方设计重写哪块、自写测试；逐款配置只作对照样本，零配置自动推导是正道。总体流程与工作包见 方案_快速通用模式.md，模式判定见 [设计_双轨.md](设计_双轨.md) §1.1。
>
> 下文 §0–§12 是 10-24 的调研、选型与 NVN 前端接口，保留作证据；其中「只在重启时切换」「就绪判定含着色器覆盖」（§11.3 第 1、2 条，§12.1 `s2a_direct_ready`，§12.3 覆盖率就绪，§12.5 提示重启）已被直连起手取代。

证据：`docs/研究/直连架构/` 下 6 份调研（1 上游直连图形栈宿主依赖、2 S2Arm 系统层图形接点、3 着色器与出包、4 宽屏、5 小菠萝与上游直连链、6 画幅线的小菠萝 NVN 栈盘点），以及 `docs/直连_NVN覆盖表.tsv` 差异列（85 条）、`docs/直连_回放差异.tsv`（51 条）。本文数字都标了来源；没测过的写「不知道，要测 X」。

## 0. 结论（10-24 修订：维护者 拟定方向 + 维护者评审，以此为准）

1. **方向：直连 = 上游直连链的「NVN → Metal」作直连专用图形层，S2Arm 只提供系统层；两模式值得共用的部分在数据层 / 库层共用，不在中间翻译层共用**（§11）。
2. 理由不只是功耗：甲（NVN → Ryujinx 渲染接口）每个 NVN 特性都要动三处（翻译层、渲染接口扩展、Metal 后端）、还要从 NVN 状态反推着色器特化，这是**结构性的长期接线成本**；成熟的 NVN → Metal 层每款几乎零接线——上游直连链 47 款里图形相关的按款开关合计约 25 次（平均每款不到 1 个），每款着色器数据由工具自动生成（§11.1）。
3. 价值依据：01006F8002326000通用 2.67 W 对上游直连链 1.89 W，省约 30%。C# 直连（甲）的功耗正在补测，只作对照：看清「渲染接口这条路的性能余量」，三条路线一起比后定首个里程碑（§8）。
4. 画面验证：不做 Mac 逐帧对拍门禁；每次直连测试局录 20 秒有动作的连续画面发 维护者，前几次过了就免检，只留崩溃 / 帧率 / 能耗自动读数（维护者 10-24）。
5. NVN 前端以已有游戏实测支撑的 NVN 语义实现为起点，不逐项复核其语义；改动记清单（维护者 10-24）。

以下 §1–§10 是 10-24 上午的调研与三方案比较，作为证据保留；§6.2 / §7 里「取舍只取决于甲的功耗」已被 §0.2 的结构性理由修订。

## 1. 第一性原理

**直连要解决的事**：把游戏发出的 NVN 图形调用，用尽量短的路径落到 Metal，换来更低的功耗与更稳的帧时间。功耗是唯一的硬目标；画面正确是前提。

**不能变的**：
- 同一个游戏核、同一套系统层（Ryujinx 深度优化版：游戏自带 SDK 原样跑，在 svc 与 IPC 处应答），存档两模式共用；
- 直连默认关，随时能退回通用；通用方案的迭代不停、不受影响；
- 宽屏不放弃（维护者 10-24）。

**奥卡姆剃刀**：直连只该替换「图形消费者」这一处。凡是为了图形之外的目的新增的实体，都要问一句能不能不要。

## 2. 取材原则

- **上游直连链为主要参照**：实现了 399 个 NVN 函数（小菠萝 204 个，小菠萝有的它全有），有条件渲染、虚拟池、几何着色器（改用计算着色器做）、间接绘制、变换反馈、顶点格式修正；01006F8002326000在测试设备 2 上 3/3 局正确到帐篷前、30 帧（证据 5）。它是外部开发者 seedds 在小菠萝开源版（d2r-mobile）基础上做的，MIT。
- **小菠萝为资料库**：我们自己的实现，122 份文档约 3.8 万行、坑.md 1989 行、41 项验证工具（证据 5）；只为暗黑 2 做过适配。
- **分叉与维护**（证据 5 §6）：上游直连链基于 d2r-mobile 10-12 首发版、收进 10-13 的脏页修复，之后各走各路；上游 311 个提交，303 个出自 seedds 一人，10-20～10-23 每天 36～52 个提交、仍在加速，本地快照 47 款、上游已 49 款。采用就 fork 一次、自己维护、按需挑上游提交。
- **S2Arm 自己的旧直连线**（证据 5 §3 与 §6，时间已核）：10-18 新架构之前，小菠萝图形层拷进 S2Arm 的 NVN 直连（HLE）线跑过01006F8002326000：10-12 出画面、10-13 进岛、10-17 真机 island_ab 905 秒 30 帧、掉帧 0.22%、**2.86 W**（`~/xbl/docs/交接/通用方案_状态板.md`）。场景与口径和上游直连链的 1.89 W 不同、不可直接比，但说明「走直连」本身不自动等于低功耗——上游直连链低在哪，要同场景测了才知道。
- **分歧裁决**：同一处两边做法不同，以「有游戏实测读数支撑的」为准；都有读数时以上游直连链为准（覆盖面更广），小菠萝的坑记录用来查它为什么这么做。

## 3. 系统层兼容（两边系统层的根本不同）

上游直连链的宿主按 SDK 函数名接管、用自己的内存池模型、不走 IPC；我们是游戏自带 SDK 原样跑、在 svc 和 IPC 处应答。但图形栈本身对宿主的依赖面很小（证据 1：用 nm 求差集，必须由宿主提供的强符号 11 个、带缺省实现的弱符号 22 个、编译期游戏宏 14 个、头文件 3 个；整栈约 2.1 万行，主体 hle_nvn.c 2323 行 + nvn_mtl.m 8492 行）。

| 图形栈的假设 | 我们的系统层怎么满足 | 谁改 |
|---|---|---|
| 客体地址 = 宿主地址；内存池零拷贝成 Metal 缓冲 | 一致（64 GB 客体窗口） | 都不改 |
| NVN 入口由宿主在 nvnBootstrapLoader 处接管 | `runtime/src/wire.c` 挂点已在；`s2a_wire_register` 收的就是 C 函数指针（wire.c:55） | 都不改 |
| 脏页跟踪：挂进宿主 SIGSEGV/SIGBUS 缺页钩子链 + 宿主写客体内存前通知 | crash.c 现在没有通用钩子链；写前通知只有一个槽（svc_mem.c:32），C# 服务层写客体内存直接调写跟踪（Compose.cs:54-58） | 系统层：两处改成链式（甲、乙都要，甲的 C# 回放也受益于统一的脏页） |
| 同一批页的写保护 | S2Arm 写跟踪（graphics/track）也写保护客体页；直连下显卡模拟闲置，理论上不碰池页，**未验证** | 规定直连开时由一方独占；要跑一局核 |
| 独占一个 CAMetalLayer、CAMetalDisplayLink 定出图节拍 | gal_present.m 也在同一个 layer 取 drawable | 直连开时由直连独占；系统层出图层不初始化 |
| 提交与等 vsync 在游戏线程同步做几毫秒 | 要接 S2Arm 的放核接口 `s2a_core_leave/enter` | 图形栈：加两行调用 |
| NVN 设备 / 队列 / 同步对象与 nvservices | 直连下游戏的 NVN 驱动不跑；但实测直连局仍初始化 nvdrv、仍向 vi 建图层（证据 2，日志 :183-188）。nvmap / as-gpu / 通道 ioctl 是否真的一次不调：**不知道，要开 IPC 记录跑一局** | 系统层：直连模式不建 GPU 通道（核实后） |
| 时间与帧步 | 服务层时间共用；帧节拍行（S2A_FPS）直连局现在 0 行 | 系统层：直连也打帧节拍行 |
| 宿主层同名不同义的函数（module_of、now_ns 等） | 冲突 | 只链上游直连链的图形部分，写一层适配；宿主层不链 |
| 通用图形初始化 | Compose.cs 与 RenderLoop.cs:169-178 不论模式都建 Metal 设备、队列、iOS 出图层、写跟踪池 | 系统层：直连 C 模式下渲染器工厂给空实现、不起渲染循环 |
| iOS 切后台的 GPU 闸门 | App 壳只叫停 NxGal 的 GPU 提交（app.m:14 写死） | 系统层：闸门改成可登记；C 实现登记进去，否则切后台被系统拒绝（证据 2b） |
| 每帧上屏计数 `s2a_frame_presented` | 测试工具靠它取帧数；现有 C# 直连自己按 60 Hz 睡眠控节拍，S2A_FPS 不生效 | 直连实现每上屏一帧调一次（证据 2b） |
| C 前端与 C# 前端同时登记 NVN 查表 | C# 的 Wire.Init 后登记会把 C 的覆盖 | 系统层：加一位开关区分两种前端（证据 2b） |
| Metal 4 + 统一内存 | nvn_mtl.m:302 无条件建 MTL4 队列、无统一内存直接退出 | 乙只能跑在 Metal 4 系统上（产品最低系统版本要核） |

**根本冲突：没有**（证据 1、2）。信号处理、出图层、写保护位都能用「直连开时由一方独占」解开；挂点同一处；地址模型一致；直连 C 实现是原生静态库，不碰「一个进程一份 NativeAOT 镜像」的约束。直连要接的点：证据 2 按细粒度数 16 个（现成 5、加一行挂接 7、新做 4），证据 2b 按大类数 9 个（NVN 入口、渲染循环分流、Metal 设备、出图层、iOS 前后台闸门、内存警告、游戏内存访问、写跟踪、日志 / 崩溃 / 帧计数），内容一致；新做的 4 个是（模式判定与 `s2a_mode_request`、帧节拍、内存警告与低区登记、GPU 报错后写 fail 退回）（证据 2）——这 16 个点甲、乙都要接，不是区分项。

## 4. 着色器

- **前端是同一件事**：两边都用 Ryujinx 的着色器翻译器（上游直连链的 dmsh_xlate 就是它，dmsh_build.py:2），都直接扫 romfs 抽取，键算法相同；01006F8002326000两边抽到的键 9730 个相同、S2Arm 独有 64、上游直连链独有 36（证据 3）。
- **翻译之后不能共用**：S2Arm 以「程序 × 特化」为单位（01006F8002326000 18479 个），带支持缓冲、顶点自取、两级管线；上游直连链以单阶段为单位（9766 支）、不带特化、管线运行时建。维护者实测「9629 对 0 相同」是设计差异的必然结果（证据 3）。
- **体积与时间**（证据 3）：01006F8002326000真机包 S2Arm 1.4 GB（metallib 361 MB + 管线归档与链接库约 1 GB，换首遇零卡顿）对上游直连链 358 MB；两种模式进同一个包，01006F8002326000多 358 MB。上游直连链01006F8002326000冷烘 18 分 10 秒；S2Arm 01006F8002326000冷烘多久**不知道**（现存日志都是缓存命中，151 秒）。我们 10 款里上游直连链有配置的 5 款（01006F8002326000、01007EF00011E000、0100152000022000、丝之歌、怪猎另一区版），按01006F8002326000单样本粗估合计多约 4.6 GB；另 5 款要先做适配。
- **首遇**：S2Arm 进程内能现编、异步、从不跳过；上游直连链手机上不翻译，没抽到的直接报红、缺这个阶段（证据 3）。
- **能共用的切法**：抽取器合并（两边都拿到并集；10-24 着色器线订正：按直连键口径为 9806，原 9830 把 28 个长控制段着色器按两种口径重复计了）、S2Arm 的组合关系转成上游直连链的预热清单、S2Arm 的特化事实填进上游直连链的答案表、翻译器修复互相移植。MSL 及之后各出各的。

## 5. 宽屏

- **第一层（服务层报分辨率）、第二层（改游戏代码让游戏自己出宽图：启用表 + 跳板 + 门）、界面布局数据层，运行时与图形路径无关**，逐行核实（widen.c:30-130 读表、loader.c:281 装载、gate.c:130 门），两模式天然共用（证据 4）。
- **第三层（GAL 包装层：投影矩阵改写、放宽渲染目标、界面层收回 16:9、顶点越界外推）**：第二层生效的 4 款（01006F8002326000、01007EF00011E000、暗黑3、怪猎）界面仍靠它收回 16:9，所以直连少了它效果就和通用不一致（证据 4）。
  - 甲：包装层已在直连的渲染链里（RenderLoop.cs:169/182），**不用移植**；唯一断点是零拷贝常量缓冲（游戏 CPU 直接写、不经过上传，包装层看不到矩阵）。补法：绘制前按影子比对被绑常量区间，命中就把改写值写进暂存副本、只把这一个绑定换到副本；绝不在游戏内存上原地改。小菠萝的 ui_mat_patch 就是这个形状（证据 4）。
  - 乙：小菠萝只给暗黑 2 做了宽屏（全靠游戏代码补丁），上游直连链完全没有宽屏（固定 16:9 居中，nvn_mtl.m:8014）；第三层要在它那边重做——约 1764 行包装层胶水要用 C 重写，或用 NativeAOT 导出 C# 识别核心、ObjC 只写接口；还要补 3 个 Ryujinx 着色器补丁加的字段（证据 4）。
- **效果一致的验证**：同存档、同屏宽、同档位，通用与直连各一局，对拍命中点集合、出图宽高比、3D 镜头比、露空、中间 16:9 区与两侧画面差、矩阵漏改为 0、宽屏开关的帧时间与功耗差；负对照：关掉快照，整套放宽档的中间区必须判红（证据 4）。

## 6. 方案比较

### 6.1 一览

| 项 | 甲：NVN → IRenderer（现 C# 直连，系统移植上游直连链语义） | 乙：上游直连链图形部分整体接入 | 丙：上游直连链语义层（C）+ 我们的 Metal 后端 + 共用着色器 |
|---|---|---|---|
| 画面正确性 | 现在：01006F8002326000进岛、人物脸手 / 树干 / 杂草纯黑；已知语义差 85 + 51 条（差异表），按表移植有界；GAL 表达不了的 NVN 语义要给 graphics/metal 加扩展（按阶段程序合成、alpha-to-coverage、遮挡计数、贴图类型适配等） | 上游直连链01006F8002326000 3/3 正确到帐篷前、30 帧（证据 5）；它的 47 个配置覆盖我们 10 款中的 5 款，另 5 款要适配；「47 款可玩」是它自述、没有逐款帧时，按我们的标准要重测 | 语义层成熟度同乙；后半段同甲（同样要面对 GAL / 我们后端的表达缺口） |
| 着色器 | 与通用共用，包体 +0；首遇可现编 | 另出一套：01006F8002326000 +358 MB、冷烘 18 分 10 秒、5 款约 +4.6 GB；缺的着色器无兜底 | 共用；但要按我们的绑定约定重写 nvn_mtl.m 的参数缓冲 / 支持缓冲 / 顶点自取 / 两级管线（证据 3：「做完等于回到 C 档」） |
| 存档 | 共用（系统层同一套） | 共用 | 共用 |
| 宽屏 | 第一、二层共用；第三层只差「绑定时快照」一个入口 | 第一、二层共用；第三层重做（约 1764 行或导出 C# 核心） | 第三层同乙（绕开了 C# 渲染链） |
| 调试工具 | GAL 录像、Vulkan 参照、逐绘制对拍全部可用（这次定位黑物体就靠它们） | 不可用；它自带一套诊断（DM_* 开关） | 部分可用 |
| 性能上限 | **不知道**——从没在真机测过。已见结构性开销：同 2 帧直连发 154,805 条 GAL 调用、通用只发 12,815 条（每次绘制全量设状态约 18 条）；另有 C# 回放与 ThreadedRenderer | 实测01006F8002326000 1.89 W（AccumulatedSystemLoad，3 局中位；同场景通用 2.67 W，1 局） | 不知道；去掉 C# 但保留 GAL 形状 |
| 系统层 / 接缝 | 16 个接点（证据 2）；已在通用的 IRenderer 链上 | 同 16 个接点 + 写跟踪链式化 + 出图层独占 + 适配层（同名函数）+ 编译期游戏宏改运行时 + Metal 4 限定 | 同乙 |
| 代码与维护 | 一套图形后端、一套着色器、一套宽屏 | 两套图形后端、两套着色器流水线、两套宽屏；上游直连链外部单人维护，fork 后自己维护 | 两套半 |
| 工作量（已知量） | 136 条差异 + GAL 扩展 + 绑定时快照 | 16 接点 + 适配层 + 着色器流水线进出包 + 宽屏第三层重做 + 5 款适配 | 乙的接入量 + 重写回放层绑定 |

### 6.2 推理

- 甲在「共用」上全占优：着色器、宽屏、调试工具、出包、维护都只有一套；它缺的是**已证实的正确性**和**未证实的性能**。正确性可以靠把上游直连链的语义系统移植过来补（参照代码现成，差异表已列）；性能如果卡在结构上（C#、渲染接口包装链、每次绘制全量设状态），移植语义补不回来。
- 乙在正确性和性能上**已被证实**；代价是两套着色器、两套宽屏、两套后端，以及失去现成的调试工具。这些代价是确定的、可以算的。
- 所以两者的取舍只取决于一个数：甲的功耗。
- 丙：语义层用 C 写成上游直连链那样，下面仍接 GAL 形状的后端与我们的着色器——它要重写直连回放层的绑定部分（证据 3），又和乙一样绕开了 C# 渲染链上的宽屏与工具。正确性不如乙确定、共用不如甲，**被支配**，不推荐。

### 6.3 不做的事
- 不把甲、乙同时做到产品级。测出功耗后只留一条。
- 不在测功耗之前继续修 C# 直连的黑物体（维护者 10-24 已停）。

## 11. 推荐架构：直连专用图形层 + 数据 / 库层共用（10-24 修订）

### 11.1 为什么换方向（长期接线成本）
- NVN 是固定接口（约 536 个函数），所有游戏共用；实现做对之后，每款新游戏图形侧的增量应趋近零。
- 甲把 NVN 语义翻成「为模拟任天堂显卡设计」的 Ryujinx 渲染接口，形状不同：按阶段绑程序、alpha-to-coverage、遮挡计数、1D 贴图、贴图类型适配、零拷贝常量与宽屏改写……每个特性都要动翻译层 + 渲染接口扩展 + Metal 后端三处；还要从 NVN 状态反推 Ryujinx 着色器特化（01006F8002326000 9267 组里 9204 组多特化）。这是**永久**成本，不是补完差异表就结束。
- 成熟的 NVN → Metal 层（上游直连链）一处就够：上游直连链 52 个游戏配置里，图形相关的按款开关在 47 款中合计约 25 次（tex_flush_upload 5、tex_dirty_upload 4、render_cond 3、tex_dyn_slots 3、present_interval 3、其余各 1–2），配置其余字段是系统层 / 打包；每款着色器数据（shader_facts / shader_map 等）由工具生成（上游快照 `dm/games/*/game.tsv` 统计，10-24）。

### 11.2 结构
```
游戏核 → 装载器 → 服务层（Ryujinx 深度优化版）/ 存档 / 输入 / 音频 / App 壳 / 模式切换     ← 两模式共用
图形（启动时二选一，同一次运行只有一套）：
  通用：游戏自带 NVN 驱动 → Ryujinx 显卡模拟 → 渲染接口 → 宽屏包装层 → graphics/metal
  直连：NVN 前端 → 直连 Metal 后端（+ 宽屏核心库调用）
数据 / 库层共用：宽屏第一、二层（本来就与图形无关）；宽屏第三层识别 / 改写核心（纯函数库，NativeAOT 导出）；着色器抽取与键；模式选择 / 就绪 / 退回
```

### 11.3 设计约束（维护者评审，维护者 已看）
1. **只在重启时切换，两套图形不同时在**：写跟踪（上游直连链靠缺页信号 + 写前通知）和出图层都是独占资源，启动时二选一、每样只有一个主人。直连模式下游戏剩下走老显卡接口（nvdrv / vi）的调用，系统层回「没东西可画」，不再出一遍画面。
2. **就绪判定含着色器覆盖**：通用模式下见过的每个着色器，直连库里都已有才算就绪；借 S2Arm 进程内翻译器现编只当最后一层保险（同步等会卡）。
3. **宽屏第三层共用库在渲染路径上零分配**：C 层在游戏线程上调 C# 导出函数，一分配就引发 GC 停顿；在真机发布版上量。
4. **Metal 底层先不抽共用代码**：等真有一个修复两边都要改时再抽那一块；首个里程碑不含。
5. **NVN 前端代码放 `graphics/nvn/`，改动记清单**（同 `compat/改动清单.md` 的做法）；代码来源与 MIT 许可见 README 致谢节。
6. **备选（不改主方向）**：直连着色器不打进包，通用模式边玩边按收集到的着色器在手机后台编，省 358 MB；代价是后台编译耗电。维护者 说过存储不是约束，原方案出两套库可以，等功耗读数再看值不值。

### 11.4 首个里程碑
待 M0（C# 直连功耗）读数出来、三条路线一起比后提案。预期形态：NVN 前端图形层 + 适配层（只链图形部分），01006F8002326000在 Mac 上直连到 MARK、录 20 秒画面给 维护者 看；接着测试设备 2 功耗与 1.89 W 对照。

## 12. 双轨接口约定（10-24，直连线总设计；各线按此对接）

总原则：两种图形只在重启时切换，同一次运行只有一套；每样独占资源（写保护、出图层、缺页信号）只有一个主人；跨语言接口一律 C ABI、参数 blittable、不跨边界抛异常。NVN 前端代码放 `graphics/nvn/`（直连线），改动记 `直连图形层改动清单（维护方内部文档）`（10-25 已冻结），来源与 MIT 致谢见 README。

### 12.1 图形模式开关（直连线提供，各线只读）
- 头文件 `runtime/include/s2a_gfx_mode.h`：
  - `int s2a_gfx_mode(void);` 返回 `S2A_GFX_GENERIC`（0）/ `S2A_GFX_DIRECT`（1）。装载器重定位前判定一次，之后只读。
  - `int s2a_mode_request(int mode, const char *reason);` 写下次启动的选择（`Documents/wire/<程序号>/mode`），不在本次运行内切换；返回 0 成功。
  - `int s2a_direct_ready(void);` 本款直连是否就绪（§12.4），给界面提示重启用。
- 判定依据（先到先得）：开发用环境变量 `S2A_GFX=direct|generic`；产品读 `Documents/wire/<程序号>/mode` → 包里带本链直连库 = 直连，否则通用（10-26 起旧的 `fail` 起局删掉、不作依据，运行中不切换）。判定写 host.log 一行「图形模式：直连 / 通用（依据 …）」。
- C# 侧 `[DllImport("s2a_native")] static extern int s2a_gfx_mode();`。直连时：渲染器工厂给空实现、不起渲染循环、不建 NxGal 的 Metal 设备与出图层（直连线改 `services/aot/Compose.cs`、`graphics/loop/RenderLoop.cs`）。
- 旧 `S2A_WIRE`（C# 直连原型）在 C 直连接通后删除。

### 12.3 着色器线：直连着色器库
- 抽取合并：合并成一套抽取器，一律按 **直连键口径**出键（控制段取 [0x760,0x880) 内的自报长度，否则截到 0x880，同 shader_split.py ctl_len；S2Arm nxsh_extract 原取完整自报长度，控制段长于 0x880 的着色器两边键不同）。01006F8002326000按此口径：交集 9754、S2Arm 独有 40、上游直连链独有 12、并集 9806。keys.tsv 与 seen 都用这一个口径。
- 包内布局（沿用直连图形层的库格式）：随资源包走（10-24 改，同通用着色器的数据口径，不进 App）——`<资源包>/shaders/direct/b-<链版本>/<键>_b.metallib`、`<键>_b.json`，以及 `shader_map.tsv / shader_facts.tsv / c1_full.tsv / cb_extent.tsv / pso_manifest.tsv`、`keys.tsv`（键清单），运行时即 `S2A_GAME_DATA/shaders/direct/`。直连线起局时设 `DM_MSL_DIR` / `DM_NVN_SHMAP` 指过去（`graphics/nvn/host_adapt.m`）。
- 覆盖率就绪：通用模式下着色器线在着色器路径上把见过的键追加写 `Documents/wire/<程序号>/seen_shaders.tsv`（一行一个十六进制键、去重）；就绪 = seen ⊆ keys.tsv（直连线的就绪判定读）。
  - seen 的键怎么来（着色器线 10-24，实施口径）：通用模式只看得到客体代码（抽取机器码去掉 NVN 0x30 字节头、截到翻译长度；计算着色器带 0x12345679 头的跳 0x100），算不出控制段键。出包时着色器阶段烘焙顺手出 `shaders/guest_keys.tsv`（客体代码 sha256 前 16 位 → S2Arm 键），`pack/stage_direct.sh` 经 `direct/key_map.tsv` 换成 `direct/guest_key.tsv`（→ 直连键，一码多键全列）；运行时 Ryujinx `S2ASeen`（补丁 direct-seen）在 ShaderCache 建出新程序时按客体代码查表写键，查不到写 `code:<客体哈希16>`，它永远不在 keys.tsv 里，就绪自然不成立。直连线读时整行比对。
  - 判定口径（10-24 写死，审 #157 / #147 定；运行时 `s2a_direct_ready` 与离线工具 `tools/direct_ready.py` 必须同口径）：
    - 行格式：每行去掉行尾 ASCII 空白（空格、TAB、CR、LF）后，必须正好是 16 位小写十六进制键；空行忽略。keys.tsv 里出现别的内容 = 输入错。seen 里不是 16 位十六进制键的行（包括 `code:<机器码哈希16>` 兜底）一律**计入缺口**。
    - 就绪 = seen 至少有一个键 **且** 缺口为 0。**空 seen（文件不在或没有有效行）判未就绪**：没有依据就不切直连。
    - 覆盖率按唯一键算；缺口清单按 seen 里出现次数降序，同次数按整行字节序升序（`code:` 行与十六进制键同一规则排，不另设特例）。出现次数只是输入行数，不代表游戏调用频次。
- 兜底现编（只当最后一层保险）：C ABI（NativeAOT 导出）`int s2a_dsh_compile(const char *key16, int stage, const void *code, size_t code_len, const void *ctl, size_t ctl_len, const char *out_dir);`（10-24 着色器线实施：传控制段而不是 cb1——切 VertexA/B、取 c1、transform feedback 都要读控制段；code = 含 0x30 字节 NVN 头的机器码区，stage 0 vs / 1 ps / 2 cs / 3 gs）同步、成功返回 0，按上游直连链格式写 `<out_dir>/<键>_b.metal/.json`（iOS 上运行时编出的库存不成 metallib：载入端只有 .metal 时用 newLibraryWithSource；实现 graphics/tools/direct/dsh，对拍01006F8002326000 9794 键与离线链一致）（`out_dir` = `Documents/wire/<程序号>/shaders/`）。直连线在上游直连链缺着色器处调它，并打「直连着色器现编 N 次」。
- 宽屏顶点越界外推（SPIR-V 改写）在直连库的离线构建里同样做一遍（调宽屏线的 SPIR-V 变换，§12.4）。
验收：01006F8002326000直连局现编次数 = 0。

### 12.4 宽屏线：第三层核心纯函数库
- 头文件 `graphics/widen/export/s2a_widen.h`，NativeAOT 导出，前缀 `s2a_widen_`。具体函数清单由宽屏线提，必须覆盖直连回放的这几处调用点（直连线在直连回放层里调）：
  - 10-24 宽屏线草案（分支 widen/corelib-1024 提交 a32dd404 的 `graphics/widen/export/s2a_widen.h`）：起局 `s2a_widen_init(screen_w, flags)` 回模式；每笔绘制顺序 targets → 每槽 `cbuf_bind(stage,slot,cpu,len)` → `s2a_widen_draw(in,out)`（定画法与外推参数 push[4]）→ `map_viewport / map_scissor` → 每槽 `cbuf_emit(stage,slot,scratch,cap)`（>0 绑暂存区，0 零拷贝绑原内存）。第 4 点因此拆成 bind + emit 两步：同一段常量要原值还是改写值，看完整笔绘制才能定。直连线确认采用。
  1. 帧开始 / 结束（屏宽、档位、帧号）；
  2. 建渲染目标：给 (宽, 高, 格式, 用途) → 放宽后的 (宽, 高)；
  3. 视口 / 裁剪变换；
  4. 绘制前常量缓冲：给被绑区间的 CPU 指针、长度、阶段、槽号 → 有命中时把改写结果写进**调用方给的**暂存区并返回改写个数，0 = 照原样零拷贝绑定；绝不写游戏内存；
  5. 上屏：界面层收回 16:9 的裁剪 / 缩放参数；
  6. 离线：SPIR-V 顶点越界外推变换（给着色器线的出包流程调）。
- 约束：渲染路径上零分配（每次调用不分配托管内存，在真机发布版上量）；可在非主线程调；通用模式先切到这个核心、宽屏门禁 30/30 不变，再给直连用。
验收：宽屏门禁 30/30 不变；零分配实测；直连01006F8002326000宽屏。

### 12.5 用户体验线（后续）：提示重启
